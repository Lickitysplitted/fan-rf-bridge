# Fan RF Bridge

Control RF-remote ceiling fans from Home Assistant, with two-way tracking: the
bridge transmits fan commands and also listens to the handheld remotes, so HA
stays in sync when someone uses the remote.

Hardware: a [wESP32](https://wesp32.com/) (PoE ESP32) running ESPHome, plus a
custom HAT carrying 433 MHz and 315 MHz ASK transmitters (NiceRF STX882) and
receivers (NiceRF SRX882S).

> **This is a reference build, not a drop-in config.** Every remote ID and
> code in this repo belongs to my remotes, and the entity names match my
> five fans. Flashed as-is, it will control nothing of yours. Capture your own
> remotes and replace the codes first; see
> [Using it with your own fans](#using-it-with-your-own-fans) and
> [Adding devices](#adding-devices). Other fan models need their own decoding.

Supported fans (one transmitter per band drives every fan of that model; each
remote has its own ID):

| Model | Remote FCC ID | Band | Encoding | HA entities |
|---|---|---|---|---|
| A | 2ABUP-FT0317A | 433.92 MHz | 40-bit PWM: 24-bit remote ID + cmd byte ×2 | 6-speed fan + reverse button |
| B (Harbor Breeze) | A25-FA0188A | 315 MHz | Manchester OOK, replayed raw | 3-speed fan + light |

## Using it with your own fans

The remote IDs in `fan-control.yaml` and `fanb_codes.h` are for **my** remotes.
Even fans of the same models need changes: each remote has its own ID. Rename
or remove fan entities to match how many fans you have. To use your own:

1. Capture each remote (see [Capturing a remote](#capturing-a-remote)), or with an RTL-SDR and
   [rtl_433](https://github.com/merbanan/rtl_433) (`rtl_433 -f 433.92M -A` /
   `-f 315M -A`; 315 MHz needed low gain, `-g 9.9`).
2. Fan A: the 24-bit remote ID is the first 3 bytes of each frame; replace the
   `prefix:` strings and the `rid ==` checks in the RX lambda.
3. Fan B: replace the pulse tables in `fanb_codes.h` (decoded from the
   triq.org links rtl_433 prints).

Other remotes need their own decode, but the TX script / RX lambda / echo
suppression pattern carries over.

## Building the firmware

Replace the remote codes with your own first (see above). The capture step
below can run on the bridge before any codes are in.

```sh
pip install esphome
cp secrets.example.yaml secrets.yaml        # then fill in a key
esphome run fan-control.yaml                # first flash over USB/serial
esphome run fan-control.yaml --device <ip>  # later updates over the network
```

The wESP32's V+ defaults to 12 V; **bridge its 5 V jumper** before fitting the
radios.

## Adding devices

### Capturing a remote

The bridge can capture by itself. Temporarily add `dump:` to the receiver for
the band, flash, and watch the log while pressing each button a few times:

```yaml
remote_receiver:
  - id: rx433            # or rx315
    ...
    dump: all            # tries ESPHome's built-in decoders, then prints raw
```

```sh
esphome run fan-control.yaml --device fan-rf-bridge.local
esphome logs fan-control.yaml --device fan-rf-bridge.local > capture.txt
```

- If a built-in decoder (`rc_switch`, `nexa`, ...) recognises it, the log
  prints a ready-made transmit action. Use that and skip the raw tables.
- Otherwise you get `Received Raw:` lines: microsecond durations, positive =
  carrier on, negative = off. Each button repeats the same burst; diff the
  buttons to find the ID and command bits.
- The SRX882 stretches marks by up to ~150 µs on strong signals, so match on
  short/long rather than exact times (`fanb_match` does this).
- Remove `dump:` when done; it floods the log.

rtl_433 with an RTL-SDR does the same from a PC and auto-decodes many
protocols: `rtl_433 -f 433.92M -A` or `-f 315M -g 9.9 -A`. The original codes
in this repo came from those captures (`fanA-433.txt`, `fanB*-315.txt`).

Only 433.92 and 315 MHz OOK/ASK devices work with this hardware. FSK remotes,
other bands, and rolling-code devices (garage doors, cars) won't.

### Another fan of an existing model

**Model A** (needs its 24-bit remote ID, the first 3 bytes of a frame):

1. Copy the `Fan A1` block under `fan:`. Rename everything `a1` in it (`name`,
   `id`, the `&a1_speed` anchor and its `*a1_speed` alias, `id(fan_a1)` in the
   speed lambda), and put the new remote's ID as a 24-bit binary `prefix:` in
   both `script.execute` calls.
2. Copy a `Fan A1 Reverse` button with the same prefix.
3. In the `rx433` lambda, add the ID to the lookup:
   `rid == 0x00CE17 ? id(fan_a1) : rid == 0x114017 ? id(fan_a2) : rid == 0xNNNNNN ? id(fan_a3) : nullptr`.

**Model B** (replayed raw, so the pulse tables are needed):

1. In `fanb_codes.h`, grow `FANB[3][5]` to `FANB[4][5]` and add a row with the
   five raw trains (speed1, speed2, speed3, off, light), in that order.
   Different remote revisions use different command bytes (see the B3
   comment), so capture every button.
2. In `fanb_match` (same file), change `f < 3` to `f < 4`.
3. Copy the `Fan B3` block under `fan:`, rename `b3` → `b4` throughout
   (including `id(fan_b3)` in the speed lambda), and use `fan: 3` in its
   script calls.
4. Copy a Fan B light: the `out_light_b3` template output (with `fan: 3`)
   and its `light: binary` entry pointing at the new output.
5. In the `rx315` lambda, extend the two `fi == ...` chains to include the new
   fan and light.

### A different kind of device

Follow the same pattern as the fans:

1. **Capture and decode** (above). Note whether a command is absolute
   (e.g. "speed 2") or a toggle (e.g. "power"). Toggles can get out of step with
   HA, as with Fan A power.
2. **Transmit.** Add a script modelled on `fanb_send`. Use a built-in action
   if `dump: all` found one, otherwise `transmit_raw` with the timings.
   Real remotes repeat a frame 5–10 times, so do the same. Keep the script's
   two guards: skip sending while `from_rx` is set (so an RX state update
   doesn't retransmit) and set `last_tx` (so the bridge ignores hearing
   itself).
3. **Entities.** Pick a fitting `template` type (fan, light via a template
   output, switch, button) and call the script from its actions.
4. **Receive (optional).** Add a branch to the band's `on_raw` lambda that
   matches the frames, ignores repeats within 1 s, and publishes the new
   state with `from_rx` set.

Before the firmware existed, codes were first checked by replaying them with a
HackRF (`make_fana_iq.py` / `make_fanb_iq.py` → `hackrf_transfer -t`). You can
skip that step and test straight from the bridge.

## Operating it

**Adding to Home Assistant.** Plug the bridge into a PoE port. HA discovers it
under Settings → Devices & services as "Fan RF Bridge"; click Configure and
paste `api_encryption_key` from `secrets.yaml`. Give it a DHCP reservation so
OTA updates keep finding it (`fan-rf-bridge.local` also works).

**Entities.**

| Entity | What it does |
|---|---|
| Fan A1, Fan A2 | On/off and 6 speeds |
| Fan A1 Reverse, Fan A2 Reverse (buttons) | Flip the direction (summer/winter) |
| Fan B1, Fan B2, Fan B3 | On/off and 3 speeds |
| Fan B1 Light … Fan B3 Light | Fan light on/off |
| Status LED | The LED on the HAT (turn off if it bothers you) |

Use them like any HA fan or light: dashboard cards, voice assistants,
automations, scenes.

**Using the handheld remotes.** Keep using them. The bridge hears every press,
so HA updates to match within a second.

**State can drift.** The fans don't report back, so HA only knows what it
sent or heard. If a press is missed (remote out of range, bridge rebooting,
fan switched at the wall), HA shows the wrong state. To fix it, set the fan or
light in HA to what it really is, then press the button once more:

- Fan A power is a toggle. If HA says off while the fan is spinning, turn it
  "on" in HA (no change on the fan), then off.
- Fan B lights are a toggle too. Same fix: flip the HA light once to match,
  then use it normally.
- Fan B speeds and off are absolute, so they can't drift. Picking a speed
  always lands on that speed.

After a reboot or power loss everything shows off in HA, whatever the fans are
actually doing.

**Status LED.** Steady on = running normally. Slow blink = warning (e.g. HA not
connected yet). Fast blink = error.

**Updating firmware.** `esphome run fan-control.yaml --device fan-rf-bridge.local`.
It needs `ota_password` from `secrets.yaml`.

## Notes

- RF is one-way per command; fan state in HA is assumed, corrected by RX when a
  remote is used. Fan A power is a toggle code; Fan B light is a toggle.
- The bridge hears its own transmissions, so RX is ignored for 2 s after TX.
- Datasheets: wESP32 product brief (silicognition.com), NiceRF STX882 / SRX882
  (nicerf.com).
